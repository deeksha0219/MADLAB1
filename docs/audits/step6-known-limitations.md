## 1. Executive Summary

This document enumerates the intentional architectural boundaries, technical limitations, and non-goals of GrabNGo Step 6 (Menu, Canteen, and Catalog Backend). These limitations are strictly intentional to satisfy security and safety rules.

---

## 2. Documented Limitations & Scope Constraints

### 2.1 Staging Environment Invariance
- **No Functions in Staging:** Google Cloud Functions deployment requires the Firebase Blaze (pay-as-you-go) billing plan. Because billing upgrades are strictly prohibited, Cloud Functions are compiled, integrated, and verified **exclusively against the local Firebase Emulator Suite**.
- **No Rules in Staging:** Staging Firestore contains only the Step 4 Ruleset. Step 6 Security Rules must NOT be deployed without a separate formal deployment review and written authorization.
- **Staging Must Remain Untested:** Step 6 tests run 100% against synthetic local emulator fixtures.

### 2.2 Functional Scope Exclusions (Deferred to Subsequent Steps)
- **Cart & Total Calculations:** Cart logic remains isolated in client state. Authoritative server-side price calculation and total validation during cart checkout is deferred to Step 7.
- **Checkout, Orders, & Order Processing Queue:** Order creation, order states (`placed`, `preparing`, `ready`, `collected`), and order history remain out of scope for Step 6.
- **Payments & Gateway Integration:** Payment verification and Razorpay/UPI integration are out of scope.
- **Push Notifications & FCM:** Order alerts and menu updates via Cloud Messaging are deferred.
- **Legacy Collection Migration:** The unhardened legacy `menu` and `cart` root collections are untouched. Legacy data is neither copied nor modified.

### 2.3 Media & Image Handling
- **No Cloud Storage Bucket Integration:** Step 6 validates image URLs as safe HTTPS strings. Direct image upload, resizing, and Cloud Storage bucket IAM rules are deferred.
- **Fallback to Local Bundled Assets:** When remote URLs are not configured in Firestore, the client gracefully displays bundled asset illustrations.

### 2.4 Idempotency & Concurrency
- **Deterministic Document IDs:** Document creation methods generate deterministic IDs where appropriate (e.g., category slug or canteen code) or secure Firestore autogenerated IDs with collision prevention.
- **Retry Safety:** Functions use transactional existence checks before performing writes.

## 3. Deployment Safety Protocol & Rollback

### 3.1 Pre-Deployment Verification
Before any future deployment to staging can be contemplated:
1. Formal staging readiness review must be conducted.
2. A separate Blaze plan exception or mock Functions deployment strategy must be agreed upon.
3. Explicit user authorization must be provided.

### 3.2 Rollback Procedure
If any local issue arises:
```bash
git checkout development
git clean -fd
```
The codebase returns to the pre-Step 6 baseline with zero residual side-effects.
