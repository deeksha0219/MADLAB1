# Step 9 Audit — Payment Threat Model and Trust Boundaries

## 1. Threat Model Overview
The GrabNGo payment architecture operates on a zero-trust model regarding mobile client assertions. The mobile application is an untrusted presentation tier that executes on student devices. Any data, request, or claim originating from the mobile device is subject to manipulation, tampering, replay, and race condition exploits.

All payment authorization, pricing calculations, state transitions, idempotency deduplication, and refund lifecycles are strictly governed by trusted server-side Cloud Functions and Firestore security rules.

---

## 2. Untrusted Inputs Inventory
The following client inputs are explicitly untrusted and MUST NOT be accepted as authoritative:
1. **Mobile client request body**: May contain manipulated payloads, unexpected fields, or prototype pollution attempts.
2. **Client-supplied order ID**: Must be verified for existence, student ownership, and matching canteen assignment.
3. **Client-supplied payment ID**: Cannot be used for authorization or state lookup without verifying parent order relationship and caller identity.
4. **Client-supplied amount / `amountInPaise`**: Client has zero authority to declare payment or refund amounts.
5. **Client-supplied currency**: Must be rejected if not `INR`.
6. **Client-supplied payment method**: Must match allowed payment methods configured for the order and canteen.
7. **Client-supplied payment status**: Clients cannot assert that a payment has started, succeeded, or failed.
8. **Client-supplied student UID**: Any UID passed in the request body is rejected; only `context.auth.uid` is trusted.
9. **Client-supplied canteen ID**: Ignored; derived solely from the server-side order document.
10. **Client-supplied idempotency key**: Must be validated, sanitized, and combined with server-computed request fingerprints.
11. **Client-supplied provider reference**: Cannot be supplied by client; generated by trusted server or verified provider.
12. **Client-supplied refund amount**: Always derived from the immutable server-side payment record.
13. **Client-supplied webhook body & headers**: Subject to cryptographic HMAC verification before parsing or processing.
14. **Replayed requests**: Mitigated via atomic Firestore transaction checks, idempotency keys, and request fingerprints.
15. **Concurrent requests**: Guarded with transactional locking and atomic state preconditions.
16. **Stale mobile state**: Rejected when preconditions do not match active Firestore document versions.
17. **Forged admin claims or role fields**: Client-supplied roles or custom tokens are ignored; verified strictly against `/admins/{adminUid}` in Firestore.

### Explicitly Forbidden Client Assertions
The client is **never** trusted to assert any of the following fields:
```
amount
amountInPaise
currency
paymentStatus
orderStatus
studentUid
canteenId
provider
providerReference
refundStatus
actorRole
createdAt
updatedAt
```

---

## 3. Trusted Sources Inventory
All security, financial, and business decisions rely exclusively on these trusted sources:
1. **`context.auth.uid`**: Cryptographically authenticated by Firebase Authentication.
2. **Server-side order document** (`/orders/{orderId}`): The authoritative record of order status, canteen assignment, and student ownership.
3. **Server-side immutable pricing snapshot** (`order.pricing`): The exact total and line-item prices computed server-side from active catalog items at checkout.
4. **Server-side payment document** (`/orders/{orderId}/payments/{paymentId}`): The single source of truth for payment attempt status, amount in paise, and refund status.
5. **Server-side admin assignment document** (`/admins/{adminUid}`): Verified for active status and assigned `canteenIds`.
6. **Verified webhook signatures**: HMAC-SHA256 signatures validated against raw request bytes using constant-time comparison (`crypto.timingSafeEqual`).
7. **Firestore transaction read versions**: Guarantees serializable isolation and detects concurrent mutation.
8. **Server timestamps** (`admin.firestore.FieldValue.serverTimestamp()`): Immune to device clock tampering.
9. **Server-owned idempotency records** (`/users/{studentUid}/paymentRequests/{idempotencyKey}`): Maintained strictly server-side to guarantee exactly-once processing.

## 4. Threat Mitigations Matrix

| Threat | Attack Vector | Server-Side Mitigation |
|---|---|---|
| Price Tampering | Client sends `amount: 1` for a ₹500 order | Server rejects client amount; reads `order.pricing.totalInPaise` directly from Firestore. |
| Double Payment | Client completes two attempts concurrently | Transaction verifies `order.paymentStatus !== "succeeded_demo"`; second attempt fails precondition. |
| Payment Bypass | Client writes `succeeded_demo` to Firestore | Firestore security rules deny all direct client writes (`allow write: if false`). |
| Read Leakage | Client queries unmasked payment records | Direct client reads denied in rules; callable `getPaymentStatus` masks provider refs and internals. |
| Idempotency Collision | Different orders reuse same idempotency key | Server binds key to `requestFingerprint = SHA256(orderId + paymentMethod + amount + currency)`; mismatched fingerprint is rejected. |
| Cross-User Access | Student A queries or cancels Student B's payment | Server checks `payment.studentUid === context.auth.uid` inside transaction. |
| Webhook Forgery | Attacker posts fake payment success webhook | Local HTTP function checks HMAC-SHA256 signature against raw body bytes using timing-safe comparison. |
| Unauthorized Refund | Client calls refund for unpaid or completed order | Server checks order terminal status (`cancelled`/`rejected`), previous `succeeded_demo` payment, and `refundStatus === "not_requested"`. |
| Attempt Flooding | Script creates hundreds of payment attempts | Server enforces max 1 active attempt and max 3 failed attempts per order. |
| Stale Expiry | User completes expired attempt | Server checks `activePaymentExpiresAt`; lazy-expires attempt if current time exceeds TTL. |
